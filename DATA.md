# Data layout

Master Repo is two things: the interface (`app/`, `tools/`, `agents/`) and a data directory of plain JSON and Markdown files. In this checkout they share one folder. To keep the data somewhere else, point `MASTER_REPO_ROOT` at it (see `app/README.md`). The app and every Python tool resolve the same folder: `app/src/lib/repository.ts` and `tools/paths.py`.

Everything below lives inside the data directory. Most missing files and folders show as empty in the app, but three pages need their file: the Overview needs `holding/direction.md` (with an `## Active conversations` section), Identity needs `identity/profile.md`, and Guide needs `guide/how-to-use.md`. The smallest data directory that runs is one `companies/<slug>/company.json` plus `holding/direction.md`. JSON `null` and `[]` mean "not known yet".

## Folders

| Path | What it holds | Format |
| --- | --- | --- |
| `companies/<slug>/company.json` | One project's model. The folder name is the slug. Folders starting with `_` (like `_template/`) are skipped | JSON |
| `companies/<slug>/wiki/*.md` | The project's wiki. `index.md` is the landing page; subfolders are fine | Markdown with front matter |
| `companies/<slug>/decisions.json` | Decisions, newest appended | JSON array |
| `companies/<slug>/card.json` | The project card: human keys plus derived keys (below) | JSON |
| `companies/<slug>/footprint.json` | Hosting, database, payments, store, domains seen in the repo, each with its file path. Env var names only, never values. Written by `tools/footprint.py` | JSON |
| `companies/<slug>/contradictions.json` | Pairs of the owner's statements the contradiction check judged, conflict or not: `[{id, a: {text, date, ref}, b: {...}, conflict, question, status: open\|resolved\|dismissed\|none, found}]`, plus `resolved` once answered. Written by `tools/contradict.py`; open ones count in the card's `owes.contradictions` | JSON array |
| `companies/<slug>/hygiene.json` | Per repo: stray root files, CLAUDE.md / AGENTS.md lines and last edit, pointer present, untracked counts, `score` with `reasons`. Written by `tools/hygiene.py` | JSON |
| `companies/<slug>/reviews/`, `notes/`, `reports/` | Dated reviews, working notes, and reports from coding agents (`tools/inbox.py note --kind report`) | Markdown |
| `companies/<slug>/threads/<date>-<topic>/` | A conversation: `thread.md` (front matter) plus `001-<role>.md` messages | Markdown |
| `companies/<slug>/builds/<id>/` | The project board: `build.md`, task briefs, run state | Markdown, JSON |
| `companies/<slug>/market/` | `market.md`, `competitors.json`, `reviews/`, `shots/` | Markdown, JSON, PNG |
| `companies/<slug>/mockups/<date>-<topic>/` | A mockup review: `index.html`, `review.md`, `notes.md` | HTML, Markdown |
| `companies/<slug>/screens/screens.json` | The app's screen map, with `notes.json` and captures | JSON, PNG |
| `companies/<slug>/git/` | `snapshot.json` and `ledger.json`, written by `tools/git_history.py` | JSON |
| `local/owner.json` | Whose data this is (below) | JSON |
| `holding/direction.md`, `vision.md` | The cross-project picture | Markdown |
| `holding/cards.md` | What a card is, for the owner | Markdown |
| `holding/calendar.json` | Dated things (`due`), planned work (`block`, with `time`/`end` HH:MM) — both with optional `steps` — and recurring checks (`check`, `cadence`, `last_done`) shown on `/calendar`. Entries with `auto` (plus `spread`, `hours`) are placed into free time by the scheduler on every read, rolling unfinished work on; `done`/`done_on` mark a due or block entry finished. The top-level `workday` (`start`, `end`, `late`, `days`, weekly `routine`) sets when auto work may go; quiet projects are added from `pulse.json` at read time. The owner edits it on `/calendar`; agents only through `tools/agenda.py` (`list`, `brief`, `add`, `move`, `done`, `step`, `remove`, `workday`), which records their thread as each entry's `source`. Both write it with two-space JSON and keep keys they don't know | JSON |
| `holding/portfolio.json`, `pulse.json` | Portfolio state; which projects are moving (generated by `tools/portfolio.py`) | JSON |
| `holding/codebases/` | Every codebase found on disk: `index.json` plus one note per repo | JSON, Markdown |
| `holding/threads/` | Cross-project conversations, same shape as a project's | Markdown |
| `holding/runs.jsonl` | One line per agent turn | JSON lines |
| `identity/` | `profile.md`, `narrative.md`, `patterns.md`, `technologies.json`, `lessons.json`, `career/` | Markdown, JSON |
| `standards/<area>.md` | Generic rules, shipped: one line each, `- <rule>. (public)`. No project names. Added through `tools/inbox.py rule --scope generic` | Markdown |
| `local/standards/<area>.md` | The owner's rules, this checkout only: `- <rule>. (<source>: <ref>, <date>)`. `evidence.md` holds the sourced originals behind shipped rules; `notes.md` holds notes on thin evidence (not rules). Added through `inbox.py rule --scope owner` | Markdown |
| `companies/<slug>/standards.md` | One project's rules under `## <area>` headings, same line format. Loads last. Added through `inbox.py rule --scope project --project <slug>` | Markdown |
| `holding/rules-condensed.json` | `{"date", "before_tokens", "after_tokens"}`: when the rules were last condensed (`skills/rules-review.md`) | JSON |
| `skills/<name>.md` | How sessions and tasks are run. `INDEX.md` is generated | Markdown with front matter |
| `local/skills/<name>.md` | Your own skills: same name overrides a shipped one, `disabled: true` hides it, a new name adds one. `python3 tools/skills.py override <name>` makes the copy | Markdown with front matter |
| `queue/*.md` | Saved questions and investigations | Markdown with front matter |
| `guide/*.md` | The in-app guide | Markdown |
| `discovery/` | Unclassified repos and new ideas | Markdown |

`agents/` (role prompts) ships with the tools. A data directory can carry its own `agents/` to override them.

## local/owner.json

```json
{ "name": "Ada Lovelace", "short": "Ada", "emails": ["ada@example.com"], "handles": ["ada"] }
```

`name` shows in the sidebar. `short` (defaults to the first word of `name`) is used in the page description, mockup notes and build directions. `emails` and `handles` tell `tools/codebases.py` which repos and commits are yours. `local/owner.md` holds how you like to work; agents read it at session start. Copy `local/owner.example.json` to start. Without the file the app says "Owner" and "You".

## company.json

`id` must match the folder name and `name` must be a string; the rest can stay `null` until known. `companies/_template/company.json` has every shared field.

```json
{
  "id": "demo",
  "name": "Demo",
  "kind": "product",
  "stage": "building",
  "one_liner": "A short line on what it is.",
  "repos": [{ "path": "/absolute/path/to/repo" }],
  "links": { "public": [], "mockups": [], "docs": [] },
  "thesis": { "why_it_exists": null, "the_bet": null, "what_it_should_become": null },
  "customer": { "who": null, "problem": null, "current_alternatives": null, "why_switch": null },
  "product": { "current_state": null, "verified_at": null, "capabilities": [], "gaps": [], "rebuild": [] },
  "roadmap": { "now": [], "next": [], "later": [] },
  "updated": "2026-10-11"
}
```

A field that holds a claim can be a plain string or `{ "text": "...", "source": "owner | agent | code | public", "ref": "...", "date": "YYYY-MM-DD" }`.

Owner values are `owner`: `source`, `raised_by`, `written_by`, thread `from`/`to`, status `awaiting-owner`, message files `*-owner.md`, and `owned_by_owner`. Older data used `alex`; `tools/master migrate` rewrites it, and readers accept both until then.

## card.json

Human keys, written by agents and the owner and never touched by tools:

```json
{
  "slug": "example-shop",
  "kind": "sell",
  "goal": { "text": "First sale through the site. Then 400 pieces.", "source": "owner", "ref": "holding/uploads/2026-10-12/dump-shop-calendar.md", "date": "2026-10-12" },
  "gates": [
    { "name": "live site", "state": "done", "note": "Next.js on DigitalOcean", "source": "owner", "ref": "...", "date": "2026-10-12" },
    { "name": "real inventory", "state": "open", "note": "sample data until INVENTORY_API_URL is set", "source": "code", "ref": "companies/example-shop/wiki/pipeline.md", "date": "2026-10-12" }
  ],
  "blocker": { "text": "eBay API keys not approved; publish and delist wait on it.", "source": "owner", "ref": "...", "date": "2026-10-12" },
  "next": { "text": "Check key status; if approved, point the site at the shop's MongoDB.", "source": "agent", "ref": "...", "date": "2026-10-24" },
  "updated": "2026-10-24"
}
```

- `kind` is the finish line: `publish | sell | client | tool | learn | maintain`. When an agent proposes it, `kind_source` is `agent`.
- `gates` are 4 to 8 operational checks (domain, hosting, database, auth, payments, store listing, landing page, hand-tested path, release build, lessons), not features. `state`: `done | open | unknown`.
- `blocker` is one operational thing in the way now; `next` is one small step.

Derived keys, overwritten by `tools/card.py refresh` (never hand-edit):

```json
{
  "moved": { "last_commit": "2026-10-12", "idle_days": 12, "commits_30d": 16, "uncommitted": 2, "branches": 0 },
  "owes": { "decisions": 1, "builds_review": 0, "builds_approved_unrun": 0, "threads_awaiting": 1, "contradictions": 0 },
  "recheck": 0,
  "footprint": { "hosting": ["digitalocean"], "database": ["mongodb"], "payments": [], "store": [], "domains": ["example-shop.com"], "public_urls_ok": null, "monthly_cost": null, "summary": "DigitalOcean + MongoDB; cost unknown" },
  "hygiene": { "stray_root_files": 3, "claude_md_lines": 410, "agents_md_lines": 0, "agent_files_last_edit": "2026-09-01", "pointer_ok": true, "untracked": 2, "score": "fair" },
  "tier": "undecided",
  "derived_at": "2026-10-24"
}
```

They come from `git/snapshot.json`, `holding/pulse.json`, `holding/portfolio.json`, threads awaiting the owner, builds, `footprint.json` and `hygiene.json`. `tools/refresh.py` runs the whole chain daily, and marks a thread or build unanswered for 14 days `status: stale` with `stale_since` (never deleted). `recheck` counts the open questions `tools/recheck.py` flagged (commits since they were asked); it isn't part of `owes`.

`tools/recheck.py` writes into the human `blocker` and `next` objects only these keys: `recheck` (the flag `{commits, since}`, or `{verdict: "resolved", reason, evidence, date, model}`), `rechecked` (date of the last agent recheck), `recheck_note` (the last verdict), `recheck_running` (while an agent works), and on a rephrase `previous` (the replaced lines, `{text, source, ref, date, replaced}`, oldest first).

## Tools

| Tool | Does |
| --- | --- |
| `card.py` | `refresh <slug>\|--all` writes derived keys; `show <slug>`; `board` prints every card |
| `footprint.py` | `scan --all [--probe]`: read-only footprint of each repo |
| `hygiene.py` | `scan --all`: read-only hygiene of each repo |
| `refresh.py` | `[--commit] [--probe]`: snapshots, pulse, footprint, hygiene, recheck flags, cards, stale marking; commits to main |
| `recheck.py` | `scan --all\|<slug>` flags open questions (threads awaiting the owner, builds in review, card `blocker`/`next`) asked before newer commits in the project's repos: `recheck_commits`/`recheck_since` front matter, or `recheck: {commits, since}` in the card line. `run <ref>\|--all` has a Sonnet agent answer resolved, rephrase or valid: a resolved thread gets a message and `status: closed`; a rephrased card line keeps its old text in `previous`; every verdict is kept in `recheck_note` with `rechecked`. Logged in `holding/runs.jsonl` as `task: recheck` |
| `contradict.py` | `check [--slug x] [--days N] [--run]` pairs the owner's dated statements (owner decisions, thread messages, notes, card lines) that share a topic and differ in date, newer within N days (default 30), and with `--run` has a Sonnet judge say whether they conflict; `resolve <slug> <id> --keep a\|b\|both` appends a decision to `decisions.json`; `dismiss`; `list`. Logged in `holding/runs.jsonl` as `task: contradict`. `refresh.py` only counts candidates |
| `inbox.py` | `context`, `note`, `mockup`, `rule`, `done`: how agents in project repos read from and write here |

## Wiki page

```markdown
---
title: Offline sync
kind: front
summary: "One sentence the cards and timeline show."
date: 2026-10-01
updated: 2026-10-11
status: open
raised_by: owner
written_by: agent
---

# Offline sync

Body in Markdown. A fenced block with the language `view` embeds a visualization by name.
```

`kind` is one of `story | front | topic | idea | visualization | redesign | history | research`. Only fronts take `status` (`open | working | settled | parked`) and `raised_by`. `written_by` is `owner` only when the words are the owner's own; missing counts as `agent`.

## Dates and paths

Dates are `YYYY-MM-DD`. Paths to other repos are absolute; paths inside the data directory are relative to it.
